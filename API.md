# TasteAI API

The FastAPI application exposes interactive OpenAPI documentation at `/docs` when running locally. JSON routes are versioned under `/api/v1`. Request schemas and response details are also defined in `tasteai/schemas.py` and `tasteai/app.py`.

## Authentication

Register/login return a short-lived bearer access token. Send it as `Authorization: Bearer <token>` for personal endpoints. Discovery and catalog reads work for guests; an invalid token supplied to a guest route is rejected rather than silently ignored.

## Location search

The request body is bounded and requires either `city` or both coordinates, never both. Result limits are 1–10. The optional `food_query` is parsed locally and is not sent to the place provider. Results are restaurant candidates only; `recommendations` remains empty in the absence of approved menu evidence. Coordinates/area and provider results are not persisted. OpenStreetMap lookup requires a descriptive `TASTEAI_OSM_USER_AGENT`; Nominatim calls are paced to at most one request per second and are subject to the current OSM usage policy.

`POST /api/v1/restaurants/discover` accepts exactly one `location_query` (1–150 characters) or a complete latitude/longitude pair. `radius_meters` is 100–50000 (default 5000), `limit` is 1–10, and optional `cuisine` (up to 80 characters) is filtered locally against provider metadata. `food_query` (up to 500 characters), optional `budget_max` (₹1–100000), and `use_taste_profile` allow the existing evidence-search path to be applied to results; profile use requires authentication. Example: `{ "location_query": "Chintalapudi", "radius_meters": 5000, "cuisine": "Indian", "food_query": "chicken biryani", "limit": 10 }`.

Food search/recommendation accepts an optional `mode`. `usual` increases the weight of previously tried/rated dishes, while `different` and `surprise` increase novelty after hard constraints; `auto` infers the mode from natural language. Responses include the parsed mode, deterministic personalization authority order, and a `pipeline` trace describing whether approved evidence or the labeled fictional catalog supplied candidates. Each recommendation includes a structured `explanation` with grounded facts, ranking components, hard-constraint status, and source citations.

The discovery response includes location resolution status, provider provenance, canonical-identity resolution state, requested bounds, `fallback_used: false`, and counts for provider results excluded because they lacked coordinates or fell outside the requested radius. Area searches are resolved first (Google Places Text Search for an area result, Nominatim for OSM), then use nearby search around that point. TasteAI recalculates geodesic distances, removes out-of-radius or coordinate-less results, and orders remaining candidates by distance. A resolved area point is not an administrative boundary; the requested radius is centered on that point. The provider may return fewer than the requested limit after local filtering. OSM `importance` is not a calibrated accuracy probability. Area/coordinates and place results are request-time only. Discovery does not create identities or provider links. A restaurant candidate is linked to stored menu evidence only when the existing identity resolver confidently matches a canonical identity; possible matches/conflicts remain separate and cannot inherit evidence. Attached evidence is from approved stored sources only and does not establish current availability. No menu facts are inferred from the place listing, and no matching evidence yields an explicit not-verified state. Tests mock all external transports; no live OSM or paid Google calls are made by this route's test suite.

## Menu evidence

`GET /api/v1/menu-evidence/restaurants/{identity_id}?limit=100&offset=0` returns normalized menu facts and provenance for that identity. `limit` is 1–100; `offset` is 0–100000. Follow `next_offset` while `truncated` is true. Only approved-source evidence is visible. The response distinguishes menu listing from explicit availability, keeps missing prices/currency unknown, and labels stale or conflicting evidence. No menu evidence is configured by default and this route does not power restaurant search or recommendations.

`POST /api/v1/menu-evidence/restaurant-identities` is reviewer-only and accepts canonical name/address/coordinates plus an optional provider name and place ID. Repeating the same provider association returns the existing identity instead of creating a duplicate. This registration step does not ingest a menu or assert dish availability; menu facts remain unavailable until an approved menu source and reviewed evidence exist. `GET /api/v1/menu-evidence/restaurant-identities/{identity_id}` exposes the identity and provider links without credentials or authorization references.

`POST /api/v1/food/evidence-search` accepts `{ "query": "Chicken Biryani under ₹300", "budget_max": 300, "limit": 10, "use_taste_profile": false }`. The query is required (1–500 characters); `budget_max` is optional (₹1–100000) and `limit` is 1–50. It searches only stored, approved, supported/verified menu evidence using exact normalized dish-name equality, with an approved `DishAlias` resolving to its active canonical dish; it does not broaden to unreviewed similar dishes, call a provider, or read from the fictional catalog. A budget ceiling requires fresh explicit INR price evidence for the exact variant. Unknown prices/currencies, stale prices, conflicting evidence, and prices above budget are excluded. Dietary restrictions and ingredient exclusions fail closed when evidence cannot establish suitability; menu listings alone do not establish availability. The response includes per-result provenance, evidence confidence/freshness, explicit availability state, a heuristic score with only available components, and explanations grounded in those fields. Unknown signals are omitted, not inferred. The normal `/food/search` and `/food/recommend` endpoints use this same evidence path when approved evidence matches the request, otherwise they retain the deterministic demo-catalog path.

Authenticated feedback accepts bounded learning actions such as `too_expensive`, `too_spicy`, `not_spicy_enough`, and `too_oily`. Each changes at most one Taste DNA feature by one point, never overwrites an explicit feature, records provenance as `learned`, and returns the learned feature in the response. Feedback may target either a demo `dish_id` or an approved menu `evidence_id`; evidence feedback is rejected for pending, rejected, contradicted, stale, or unapproved records.

Stale evidence is excluded by default. `TASTEAI_EVIDENCE_STALE_POLICY=downgrade` permits stale evidence only for searches without a budget ceiling; results are clearly marked stale and never assert current availability. `TASTEAI_EVIDENCE_RANKING_WEIGHTS` accepts a JSON object with `dish_match`, `evidence_confidence`, `freshness`, `price_fit`, `taste_match`, and `availability_confidence` non-negative weights; configured weights are normalized, and invalid values fail explicitly. No taste/distance/review/novelty claim is scored without corresponding evidence. `use_taste_profile: true` requires an authenticated user and considers only stored dietary requirements and preferred cuisine when evidence supports a match.

Menu photo routes are reviewer-only and require the account ID in `TASTEAI_MENU_PHOTO_REVIEWER_USER_IDS` (empty by default). `POST /api/v1/menu-photos` accepts raw JPEG, PNG, or WebP bytes with `X-Restaurant-Identity-Id`; optional `X-Menu-Captured-At` must be timezone-aware ISO 8601. Optional `X-Restaurant-Provider` and `X-Restaurant-Place-Id` must match an existing provider identity link. The request body is streamed with a configured byte limit; the decoder validates actual image type, integrity, and dimensions.

The original bytes are stored under an opaque generated key in a private local directory outside static assets, controlled by `TASTEAI_MENU_PHOTO_STORAGE_DIR`. The API never returns the key or serves image bytes. The upload creates a `MenuSource`/`MenuDocument`; no timestamp is fabricated when capture time is absent. The allowlisted reviewer is the source authorization attestor. `GET /api/v1/menu-photos/{document_id}/proposals` lists staged extraction results; `PATCH /api/v1/menu-photos/{document_id}/proposals/{proposal_id}` accepts/rejects/corrects one proposal; `POST /api/v1/menu-photos/{document_id}/commit` promotes accepted, uncommitted proposals idempotently through `ingest_menu_batch`.

OCR/Vision uses an optional OpenAI Responses adapter behind `TASTEAI_ALLOW_EXTERNAL_OCR=true`, `TASTEAI_OCR_PROVIDER=openai`, and a server-side `OPENAI_API_KEY`. It is disabled by default. When enabled, the uploaded image is sent to that provider; output is schema-validated and staged only as pending proposals. Section, description, confidence, page, and normalized bounding box remain provenance on the proposal and promoted evidence. OCR failures preserve the private upload for manual review. Each accepted proposal is promoted to verified menu evidence only by the reviewer commit route; a photo establishes a menu listing at capture time, not current availability. Unknown capture dates remain unknown and evidence without a date is stale under the freshness policy.

RAG indexing includes only `supported` or `verified` evidence from approved sources. `POST /api/v1/rag/query` applies `budget_max` as a hard ceiling and also recognizes hard budget phrases such as “under ₹300” in the query when the field is omitted. The deterministic retrieval score is `0.40 × lexical + 0.30 × max(0, cosine_similarity) + 0.20 × evidence_quality + 0.10 × freshness`. Lexical similarity is token overlap divided by the square root of the token-count product. Evidence quality multiplies state weight (`verified=1.0`, `supported=0.8`) by confidence (`high=1.0`, `medium=0.75`, `low=0.5`, `unknown=0`). Freshness declines linearly from 1.0 at the source's last-verified/captured time to 0.0 at its configured TTL; stale evidence is excluded before scoring. A record with zero lexical overlap and cosine below 0.2 is omitted. Local vectors use deterministic lexical hashing, not semantic embeddings. OpenAI embeddings require `TASTEAI_ALLOW_EXTERNAL_EMBEDDINGS=true`; provider/model mismatch falls back to lexical scoring. `POST /api/v1/rag/query` can optionally use the separately gated OpenAI LLM (`TASTEAI_ALLOW_LLM=true`) to select typed menu-listing or listed-price claims from at most five retrieved records. The query and bounded structured evidence fields are sent to OpenAI when this option is active; source descriptions and private storage paths are excluded. TasteAI independently checks each evidence ID and verifies that a listed price is present and marked known, then renders the factual text from those stored fields. Unsupported selectors are rejected, and provider failure or no supported claims falls back to deterministic cited wording. This is not general natural-language entailment checking. The response includes `generation.status`, `grounding_status`, `validated_claims`, and citations. `POST /api/v1/agent/chat` uses a fixed four-step flow and deterministic ranking; the optional OpenAI structured query extractor supplies hints only. OCR, LLM, and external embeddings are off unless explicitly configured. The Schema.org adapter still accepts supplied HTML only and never fetches a URL.

There is no public route to create restaurant identities or provider links. Trusted in-process identity/source operations remain separate. Menu-photo review access is an allowlist, not a complete role-management system; configure only trusted reviewer accounts and keep local storage protected by the host filesystem.

Errors use FastAPI's JSON `detail` response. Pydantic validates request fields; provider failures are sanitized and do not include upstream response bodies.
